# Doc To Word Converter

把 PDF、PPT、Excel、图片、扫描件和图片型 Word，整理成干净、可编辑、可复用的 Word 模板。

这个项目最早不是为了“炫技”做的。我平时会积累很多业务资料：合同模板、流程文件、表格、培训资料、外部参考文档。它们看起来都有用，但真到要拿来改、拿来复用、拿来分享时，问题马上出来了。

有的文件全是水印和页眉页脚；有的带真实公司名、人名、电话、地址；有的是 PDF、截图或扫描件，想改一个字都得重排；还有一些表格，普通工具能识别文字，但表头、合并单元格、横竖版全部乱掉。单个文件还能手工修，几十个文件一起处理时，人就开始在复制粘贴、脱敏、检查格式里打转。

`doc-to-word-converter` 就是把这些重复动作收进一条队列里：先判断文件复杂度，再按批次转换，生成 Word 后做隐私检查和质量检查。它不追求“跑得快”，更在意打开 Word 后是不是真的能编辑、能复查、能继续交给别人用。

## 从 WorkBuddy 到 Codex

这个 skill 最早是在 WorkBuddy 里做的，目标是把一堆带水印、带敏感信息、格式又不方便编辑的资料批量转成 Word 模板。后来迁移到 Codex 时，规则做了几轮调整：

- 把原来偏 WorkBuddy 的路径和调用方式，改成 Codex 可用的 skill 结构；
- 把 `TBD / Done / New` 队列模型固定下来，方便自动化反复检查；
- 加入复杂度评估，不再按固定数量硬分批；
- 每个文件完成后增加隐私检查和质量检查；
- 针对图片型表格、合并单元格、斜线表头、多级表头，补了更细的还原规则；
- 把公开文档里的真实文件名、真实业务名称、本地路径全部泛化处理。

如果你也经历过“自动转完还要人工修半天”，这个项目解决的就是那半天。

## 适合谁

- 经常把 PDF、截图、扫描件整理成 Word 模板的人；
- 做流程文件、合同模板、评价表、培训表单、费用表的人；
- 做跨境电商、项目管理、培训交付，需要把旧资料整理成可复用模板的人；
- 有一堆资料要脱敏后分享，但不想一处处手工查找替换的人；
- 想用 Codex 自动化定期检查 `TBD` 文件夹的人。

如果只是把纯文字 PDF 粗略导成 Word，普通转换工具可能已经够用。这个项目更适合那些结构复杂、隐私风险高、后续还要编辑的文档。

## 它解决什么问题

### 1. 文件多，不能靠手工排队

工作流固定为三个文件夹：

```text
TBD   待处理文件
Done  已处理原文件
New   生成后的 Word
```

你把待转换文件放进 `TBD`。Codex 每次先看状态，再评估复杂度，决定这轮处理几个。通过检查后，原文件进 `Done`，新 Word 进 `New`。

### 2. 复杂文件要单独处理

最早按“每批几个文件”处理，后来发现不靠谱。几个简单文件可以一口气跑完，一个复杂扫描件或大表格就可能把上下文塞满。

现在会先看这些因素：

- 有没有文本层；
- 页数多少；
- 有没有图片或扫描内容；
- 表格数量和复杂度；
- 是横版还是竖版；
- 是否需要 OCR 或人工视觉判断。

简单文件可以合批，复杂文件单独处理。宁可少跑一个，也不要交付一个不好用的 Word。

### 3. 横版竖版不能猜

原文件是横版，输出就应该是横版；原文件是竖版，输出就应该是竖版。这个规则看起来简单，但很多转换流程会在这里出错。

这个 skill 会先检测页面方向，再生成 Word。检测失败时才保守使用竖版，并在报告里说明。

### 4. 表格要能编辑，也要像原表

这部分是最近重点优化的地方。

早期版本犯过两个相反的错误：

- 把一张多行评价表压成几行大单元格，打开 Word 后很难逐项编辑；
- 后来又把所有合并单元格都拆开，明细能编辑了，但原表的分组结构没了。

现在的规则是：

- 明细项一项一行；
- 原表有意义的分组合并要保留；
- 斜线表头、多级表头、分组表头要尽量按源表重建；
- 不把整页截图贴进 Word 冒充完成；
- 不为了省事把多行内容塞进一个文本单元格。

### 5. 脱敏不能靠记忆

很多资料里会带真实公司名、人名、联系方式、证件号、账号信息或地址。人工处理很容易漏。

这个 skill 把脱敏拆成两层：

- 指定的旧公司或来源方名称，可以统一替换成 `****`，方便后续批量替换；
- 其他敏感信息，替换成 `[乙方公司名称]`、`[自然人姓名]`、`[联系电话]` 这类角色化占位符。

生成 Word 后，还会继续检查长数字串、手机号、邮箱、公司后缀、Word 元数据和修订痕迹。

## 自动化提示词

如果你想设置 Codex 自动化，可以直接复制下面这段。它的逻辑很简单：定时检查 `TBD`，有文件就处理，没有文件就报告为空。

```text
使用 doc-to-word-converter skill 检查当前工作区的 TBD 文件夹。
先初始化并确认 TBD、Done、New 三个文件夹存在，然后运行状态统计。
如果 TBD 为空，只报告“本轮没有待转换文件”，不要做其他操作。
如果 TBD 里有需要转换的文件或邮件附件导出的文件，先运行复杂度评估，再按质量优先原则选择本轮处理范围。
复杂、不确定、图片型、扫描型、表格结构复杂的文件，一律单独处理。
转出的 Word 横版或竖版必须根据原文档结构检测决定，不能默认横版或默认竖版。
表格还原要遵守：明细行保持独立；源表中有意义的分组合并要保留；斜线表头、多级表头、分组表头不能随意扁平化；不能把整页截图当成最终 Word。
每完成一个文件，都要运行隐私清理、隐私检查、质量检查；表格型文件还要运行表格粒度检查。
检查通过后，原文件移动到 Done，生成的 Word 放到 New。
最后报告：本轮处理了多少个文件、生成了多少个 Word、TBD 还剩多少个文件。
如果上下文变长、检查失败或文件结构不确定，停止继续批处理，并说明需要人工确认或新建对话继续。
```

更详细的自动化说明见：[Codex 自动化设置](docs/automation.md)。

## 快速开始

1. 把 `skills/doc-to-word-converter` 复制到你的 Codex skills 目录。
2. 重启 Codex，让它重新读取 skill。
3. 准备一个转换工作区，里面建好 `TBD / Done / New`。
4. 把待转换文件放进 `TBD`。
5. 对 Codex 说：

```text
使用 doc-to-word-converter skill 处理当前工作区的 TBD 文件夹。
先初始化、统计状态、评估复杂度。
质量第一，复杂文件单独处理。
每个文件通过隐私检查和质量检查后，再移动到 Done 和 New。
```

## 依赖说明

基础处理通常需要：

- Python 3
- `python-docx`
- `pypdf`
- `Pillow`

可选能力：

- `PyMuPDF`：更好地读取 PDF 页面尺寸、图片和版式；
- `pytesseract` + Tesseract OCR：处理扫描件和图片文字。

没有 OCR 依赖时，skill 仍然可以处理有文本层的 PDF、普通 DOCX、Excel/CSV 和部分可人工识别的图片型表单。它不会假装自己做了 OCR。
