# 优化记录

这个 skill 是从真实批量转 Word 需求里改出来的。最早版本跑在 WorkBuddy 里，后来迁移成 Codex skill。迁移过程中，真正有价值的不是“换了一个客户端”，而是把之前踩过的坑沉淀成了更清楚的规则。

## 1. 从单文件提示词变成队列流程

一开始，单个文件靠提示词处理就够了。文件一多，问题马上出现：复制粘贴多、容易漏脱敏、上下文越来越长，后面的文件质量不如前面的文件。

所以后面固定了 `TBD / Done / New` 三个文件夹：

- `TBD` 放待处理文件；
- `Done` 放已通过检查的原文件；
- `New` 放最终 Word。

这个队列模型让自动化有了抓手。每轮只看 `TBD`，处理完再移动文件，下一轮不会重复碰已经完成的资料。

## 2. 从固定数量分批，改成复杂度分批

早期按固定数量分批，比如一批几个文件。实际使用后发现，这个规则太粗。

一个简单文本 PDF 和一个多页扫描件，对模型和脚本的压力完全不一样。于是加入复杂度评估：页数、文本层、图片、表格、方向、OCR 风险都会影响分数。

现在的原则是：简单文件可以合批，复杂文件单独处理。质量比速度重要。

## 3. 加入上下文保护

批量处理时，越到后面越容易出问题。OCR 文本、日志、表格内容不断堆进上下文，模型会开始省略、误判或把表格看浅。

所以 skill 里加入了明确的中断规则：

- 当前对话变长时，不继续贪多；
- 复杂文件单独处理；
- 失败检查不硬过；
- 必要时新建对话继续。

这不是为了保守，而是为了让第十个文件也尽量有第一个文件的质量。

## 4. 版式方向必须先检测

横版、竖版不能靠默认值。Word 生成时如果只设置方向、不交换页面宽高，也可能看起来设置了横版，实际输出仍然不对。

现在的规则是先检测，再生成：

- PDF 看页面宽高；
- DOCX 看 section；
- PPT/PPTX 看页面尺寸；
- 图片看像素宽高。

检测失败时才保守使用竖版，并把这个情况写进报告。

## 5. 表格还原从“能看”改成“能编辑”

表格是最容易出错的地方。早期版本有时会把多行内容塞进一个大单元格，看起来信息还在，但 Word 里很难编辑。

后来又出现过相反问题：原表本来有合并单元格，用来表示分类和分组，转换时却全部拆开，结果不像原表。

现在的判断更细：

- 明细项要独立成行；
- 分组标签可以按源表合并；
- 评分标准、结果块、备注块这类跨行内容要保留结构；
- 斜线表头、多级表头不能随便扁平化；
- 不能用整页截图冒充可编辑 Word。

## 6. 质量门禁不能省

生成 Word 只是中间结果，不是交付结果。最终进入 `New` 前，至少要过这些检查：

- 元数据和修订痕迹清理；
- 隐私检查；
- 基础质量检查；
- 表格粒度检查；
- 必要时人工打开复查。

任何检查不过，都不应该把原文件移动到 `Done`。

## 7. 公开版本做了泛化处理

这个项目来自真实工作流，但公开仓库不会放具体文件名、具体业务名称、本地路径或截图。README 和文档只保留通用场景：合同模板、流程文件、评价表、费用表、扫描件、图片型 Word。

这样别人能复用方法，也不会把个人或公司资料带出去。
